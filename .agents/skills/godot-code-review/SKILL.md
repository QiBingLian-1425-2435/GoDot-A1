# Godot 代码审核

目标是让作者和非作者审核人知道：审了哪个版本、有哪些真实问题、哪些行为仍需验证。
代码审核按改动需要选择；所有成员可合并 main，不强制非作者批准。本技能保持只读，合并交给当前交付流程。必需参考均在本包，可独立使用。

## 先定位任务与规则

1. 确认用户指定的真实 PR、提交或差异范围；缺少目标时先检查当前任务上下文，不猜一个 PR。
2. 定位实际项目根与 Godot 工程根，它们可能不同；技能安装目录不是项目根。
3. 读取本包 [团队默认约定](参考/团队默认约定.md)；涉及架构时按需读 [架构与模块边界](参考/架构与模块边界.md)。
4. 包内参考相对本技能目录解析；实际项目规则与明确任务优先，没有作者仓库文档不阻塞审查。
5. 读取本次任务、采用中的接口和相关工程基线；缺少入口时说明，使用真实用户上下文，不假称已读。
6. 没有任务说明时根据真实差异审查可证实问题，明确缺少的验收上下文，不硬套示例人数、玩法或节点结构。

审核所需事实不清先查文件；只有影响结论且无法发现的信息才向用户询问。
仅文案或注释差异按实际风险审核，不强制完整架构与联机检查。

## 固定审核对象

- 记录仓库身份、PR 链接或提交范围、目标分支，以及当前 head SHA 和 base 分支 tip SHA。
- 同时记录实际差异起点：PR 通常使用共同祖先至 head；指定提交按用户要求取父提交或明确范围。
- 使用这些固定 SHA 读取差异和上下文，避免作者继续提交时审核内容悄悄变化。
- 没有 Git 时可以审明确的文件副本或补丁，但标明没有可核验提交，不伪造 SHA 或 PR。
- 使用已有工具读取 PR 元数据与差异；连接器不可用时可用已具备权限的 Git/CLI，不要求先装插件。
- 本地有无关未提交成果时保留原样；优先按 SHA 阅读或使用独立验证副本，不切换覆盖作者目录。

## 只读预审

不修改代码、场景、规则、任务状态或作者暂存区，不把审核顺手变成另一套实现。
运行验证可生成独立缓存和测试产物；避免导入或工具自动重写被审源文件，必要时在隔离副本运行。
未经用户明确授权，不向远端发送评论、审核意见或 Approve，不点击合并。
用户已明确授权发布审核意见时，只发布本次指定对象的已核验结论；发布本身不等于团队验收。

1. 先读任务目标和差异，再追踪相关调用方、资源引用与状态拥有者，避免只看片段误报。
2. 优先检查玩家可见的错误、数据破坏、联机权威、生命周期与集成兼容，不以个人风格阻挡交付。
3. 架构、资源、场景或联机变化时按需读[审核重点](参考/审核重点.md)，只选相关分支。
4. 每项问题给出实际触发条件、具体位置和影响，并说明是代码证据、复现还是待证实风险。
5. 发现超出差异的旧问题时注明既有问题；不把它冒充本次引入的阻断项。
6. 疑似问题先寻找反证与保护条件，不能证实就说明不确定，不编造运行结果。

严重度按影响判断：P0 为需立即处理的严重破坏；P1 为重要流程受阻；P2 为一般功能缺陷；P3 为低影响问题。
可选建议单列，不把新需求、审美偏好和猜想写成必须修复的缺陷。

## 用验证支持结论

- 使用任务已有验收入口，选择能验证实际改动的最小有效检查，含必要失败路径。
- 导入/解析检查、单机场景、同机两进程、真实双机、异地测试分别记录，不能互相替代。
- 没有匹配版本的 Godot 时可静态审核，明确未执行的行为、所缺环境与人类复核步骤。
- 纯文字改动检查含义与链接；不为低风险可逆文字变更新增镜像实现的测试。
- 记录执行版本、入口、操作与实际结果，区分已通过、已失败、未执行。

## 审核过程中发生新改动

结束前重新核对 head 与 base；不要把旧 SHA 的结论包装成最新版通过。
head 增加提交或解决冲突后，审查新差异并重验受影响行为；说明哪些已有证据仍可复用。
base 主线前进时检查最终组合兼容性，必要时补相关集成验证，不机械要求重跑所有无关测试。
无法取得新版本时交付已审 SHA 和差距，保留“最新版本待复查”的结论。

## 交付格式

按下面顺序给出简短、可复核报告，问题位置使用真实文件和紧凑行号。

```text
对象：真实 PR/提交；目标分支；head；base tip；差异起点。
发现：[严重度] 文件:行 — 触发条件、影响、证据；必要时指出最小修正方向。
已验：环境、入口、操作、实际结果。
未验：限制、需由谁或什么环境补验。
版本变化：是否仍为相同 head/base；新增差异与需复查范围。
交接：作者需修什么；哪些行为仍需接手者验证。
```

没有发现可证实问题时直接说“在该范围内未发现可证实缺陷”，同时保留验证限制。
不把未发现问题表述为全游戏无 Bug，不把 AI 报告写成其他成员的实际验收。
