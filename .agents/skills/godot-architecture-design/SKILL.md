# Godot 架构与模块设计

本技能可单独复制使用，必需材料均在本目录；不要求获得作者仓库的历史文档或安装其他技能。

## 开始

1. 读取 [团队默认约定](参考/团队默认约定.md)，确认本次实际项目和任务。既有有效规则、已采用接口及用户明确决定优先；缺资料时用包内默认，不因没有某个固定文档路径停工。
2. 阅读 [架构与模块边界](参考/架构与模块边界.md)。核对已有工程、相关节点与依赖，区分真实实现、采用方案和建议。没有代码就做方案，不捏造扫描结果。
3. 判断用户要讨论、落盘设计还是实施重构。设计请求默认交付设计；用户同时要求实施时，再按已明确边界推进，不把写方案当作完成代码。

## 设计到能分工

- 先写玩家可观察的最小闭环与本轮不做项，再按职责划分模块；不先为候选功能建目录或框架。
- 同时标明功能模块与内部职责：规则、引擎/网络适配、表现、编排、配置/运行态。它们是职责边界，不强制每层都拆成一个文件夹。
- 不把表现/规则分离误写成必须部署前端/后端两套服务。房主可同时承担权威逻辑和本机显示；首版不凭“架构”名义增加数据库服务或独立服务器。
- 每个关键状态指定唯一拥有者和写入入口。显示端可提意图；共享结果由权威端确认；本地相机等本机状态单独处理。
- 用本技能的 [模块与接口设计模板](模板/模块与接口设计.md) 输出职责、目录、依赖、公开接口、生命周期与验证入口，填真实信息，不编造成员姓名或工时承诺。
- 接口只定义当前协作者实际需要的参数、成功/拒绝结果和清理方式；公开方法发起动作、局部信号通知结果、上层接线。信号不是网络传输。
- 并行任务明确文件边界及公共配置、主地图、协议的当次编辑者。先合接口和最小实现，再接下游；分支不同不等于工作目录隔离。
- 缺少影响权威归属或跨模块行为的关键决定时，提出具体选项并标注待定；仍可先交付不依赖它的模块范围、目录和验证建议。

## 新需求与骨架的关系

先读项目共同目标和真实结构：已有职责内扩展就沿用模块；独立职责才新增功能目录；协议、状态拥有者或依赖方向改变才算架构调整。新物品、换表现等不自动升级成重构。说明旧/新路径、公开接口、状态唯一写入者、受影响调用方与公共文件编辑者；普通小任务用简短决定即可。

入口保留编排，机制进入所属功能模块；按被本次需求触及的职责逐步提取，不以骨架设计为由一次性重写 main。已有根目录 project.godot + docs 或 game/ 布局均可，保留实际入口，案例不是强制目录清单。新增后同步实际结构、任务与接口；方向变化同步共识，不把动态工程树抄进通用技能。

## 调整已有架构

描述具体触发问题、当前依赖、最小调整及其收益。给旧→新接口/状态映射、调用方迁移顺序和可回退基线，避免为纯表现修改重写玩法或网络。
按影响验证两实例隔离、停止装饰动画、切换测试房、重复/竞争请求和退出重进。没有运行环境就提供步骤并标未执行。

## 交付

交付最小闭环、模块职责表、英文目录映射、接口和状态流、依赖与合入顺序、验收入口及未决项。只有用户要求保存时才把实际设计写入目标项目或指定任务源，不把动态接口和任务写进技能源文件。
清楚的小任务可直接实施，不强制每次先跑完整架构设计；其他技能不可用也不阻塞本技能独立交付。
