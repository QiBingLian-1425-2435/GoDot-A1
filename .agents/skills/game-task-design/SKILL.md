# 任务与接口设计

把真实需求变成可以独立交付、能由另一人验收的任务；保持项目现有玩法与模块路线。
本技能默认产出设计和任务材料，不因写了任务就执行实现、创建线上 Issue 或调整真实分工。本包可独立分发，不依赖作者仓库文档或其他技能。

## 先找到当前事实

1. 从用户指定工作目录定位实际项目根；有 Git 时确认根、分支和基线。Godot 工程根可能在仓库子目录。
2. 读取本包 [团队默认约定](参考/团队默认约定.md)；涉及跨模块分工/状态归属时读 [架构与模块边界](参考/架构与模块边界.md)。
3. 包内链接相对本技能目录解析。实际项目的规则、任务和接口优先；没有作者的历史文档是正常情况，不要求创建或找回固定路径。
4. 阅读真实 Issue/任务卡、采用中的功能设计、相关模块和接口；区分已有实现、已采用方案、候选建议、教学例子。
5. 工程或实现不存在时写明现状。不要将教学编号、示例接口、占位姓名变成真实任务或任命。

目标和验收已经清楚时补足必要缺项即可，不强制重写整份设计或建立新流程。
影响玩法、权威归属、共享接口的未知项需要明确决定；局部实现选项可记录合理默认。

## 拆成能交付的行为

- 用玩家或使用方可观察的结果表述目标，明确本次不做什么。
- 按可演示行为拆分，不按“先全部脚本、再全部场景、最后测试”拆分。
- 每项任务有一个主责；未知姓名写“待团队指定”，给出需要的职责，不编造成员承诺。
- 沿用唯一任务源。尚未决定采用前，输出标注“草案/待确认”，不要宣称 Ready 或已安排。
- 原型实验写清假设、观察方式和结束条件；实验代码不会因存在就成为正式架构。
- 能在一至两个工作时段验证的小行为优先；估时仅供团队安排，不保证未了解的工时。

## 约定最小接口

只有跨模块连接或已有接口需要变化时，补一份短接口约定：

| 项目 | 必须明确 |
|---|---|
| 发起与接收 | 谁提出意图、谁处理、谁提供依赖 |
| 输入与结果 | 参数含义、必要类型、成功/拒绝结果；名称以真实工程为准 |
| 状态归属 | 谁保存与修改最终状态，谁只读展示 |
| 生命周期 | 初始化、清理、重复调用和失效目标的必要行为 |
| 验证入口 | 独立场景/规则入口、组合场景、验收者需要的前置条件 |

只为当前双方连接定义需要的信息，不顺带建立通用消息协议或完整接口框架。
规则接受中立输入；上层编排连接机制与表现。公开方法、局部信号、明确依赖均可，不强制全局事件总线。
多人任务区分客户端意图与权威结果；本地信号不是网络消息。

## 确定并行边界和依赖

- 给出各任务允许改/新增的目录，以及必须阅读但本次不改的共享入口。
- `project.godot`、主地图、共享接口、网络入口由真实约定中的编辑者协调，不让多个任务各造一套。
- 并行写入需要不同 clone 或正确的 worktree；分支名不同不代表文件目录隔离。
- 写明依赖任务和合入顺序。未合入接口可先做测试替身与表现，不能声称完成真实接入。
- 发现必须改公共内容时，描述最小差异、受影响模块和协调项；继续不依赖该决定的工作。
- 不因任务拆分而替用户建仓库、推送、发评论、创建 Issue 或发布。

## 每项任务的最小交付

按项目已有模板填写；没有时可用本包 [任务执行卡](模板/任务执行卡.md) 与 [模块与接口设计](模板/模块与接口设计.md)，或保留以下最小字段：

```text
目标与不做项：
状态：草案 / 按真实任务源记录
主责、备份、可选复核人：已知填实际值；不以指定非作者审核人作为开工或合并门槛
采用中的设计/接口与依赖：
允许修改、新增及共享文件协调：
验收入口、操作、预期、相关失败情况：
交付证据与未测项：
下一次交接需要什么：
```

验收至少覆盖正常结果和本次最可能失败的情况；按改动选择重复操作、无效输入或联机竞争，不机械套全套测试。
区分静态检查、本地场景、同机多进程、真实双机和异地验证；需求未覆盖的层次不能勾通过。

## 收尾

交付小任务清单、必要接口差异、依赖顺序和未决项，给出下一位执行者的最短启动说明。
如果用户只要求讨论，留在对话中；要求落盘时保存到项目既定设计/任务位置，不在技能包内记动态任务。
若继续请求实现，沿用已确认任务和现有授权进入开发，不要求先安装其他技能才能继续。
