# 目录操作与交接

按本次任务选择一节，不要求每次都走完初始化和迁移两条流程。必要默认规则和目录说明均在本包，目标项目已有正式约定优先。

## 新工程的起步判断

| 当前情况 | 做法 |
|---|---|
| 只有文档与教学示例，用户要求建立正式工程 | 单独创建英文工程目录，默认 `game/`；保留示例，不把示例直接当正式项目 |
| 已有可运行的正式工程 | 沿用实际入口；不再嵌套新建另一个 `project.godot` |
| 用户只是询问目录含义 | 解释已有结构或给建议，不创建游戏、仓库或空目录 |
| 用户只要求新增一个模块目录 | 先按模块职责定位，只增本次文件，不修改引擎版本或全局设置 |
| 已有中文目录但本次是局部开发 | 新目录用英文，记录旧目录待迁移；不批量改名 |
| 用户明确要求中文目录迁移到英文 | 列迁移映射并实施，检查资源引用和外部素材交接 |
| 找不到 Godot 可执行程序 | 完成源文件和静态检查，报告未运行；不伪造引擎版本或验收 |

同一项目中的仓库目录、工程根和 `res://` 要明确区分。例如采用 `game/project.godot` 后，仓库路径 `game/features/player/player.tscn` 对应 `res://features/player/player.tscn`，而非 `res://game/features/...`。

新增功能需要决定目录或骨架调整时，再读[新需求落位与骨架演进](新需求落位与骨架演进.md)。以下 game/ 布局仅是新工程候选，根目录 project.godot + docs/ 同样有效；优先保留实际入口。

## 推荐目录与职责

```text
we_game/                          仓库名称示例，不要求改名已有仓库
├─ .gitignore                      根规则；本包模板可用
├─ AGENTS.md                       实际任务需要统一 AI 入口时生成/合并
├─ game/                           新正式工程默认位置；这里是 res://
│  ├─ project.godot                起步所需的工程配置
│  ├─ app/                         需要入口协调时增加 main.tscn / main.gd
│  ├─ features/
│  │  ├─ player/                   玩家主体、输入与专用表现
│  │  ├─ interaction/              目标选择、提示、交互意图
│  │  ├─ doors/                    门的场景、状态和表现
│  │  ├─ items/                    物品定义与地面实例
│  │  ├─ inventory/                容量、重量与归属机制
│  │  ├─ enemies/                  鬼怪感知、导航与行为
│  │  └─ escape/                   撤离条件、等待、结果
│  ├─ worlds/prototype_room/       小地图组装、静态环境、出生点
│  ├─ ui/                          界面、HUD 与本机反馈
│  ├─ tests/                       独立验证入口，出现需求才拆
│  ├─ shared/                      确有多个模块使用的具名内容
│  └─ addons/                      实际采用的插件，保持上游结构
└─ 文档/                           可选的实际输出位置，不是本技能输入依赖
   ├─ 项目说明.md                   引擎版本、真实入口、操作与素材获取
   ├─ 项目设计/                     采用设计、模块与接口
   └─ 任务跟踪/                     没用 Issue 等任务源时再建立
```

这是一张职责地图，不是创建清单。初始只要真实工程配置、可观察的主场景及必要脚本；主场景可直接是房间，没有接线需求不强制建 app/。起步用内置几何体，不要求先下载素材或实现表中全部模块。

Player 处理角色行动，Interaction 提意图，门/背包等管理自己的机制，上层串联校验与结果，UI 只展示并发请求。共享结果由权威端确认，状态归属在真实接口中写明；不存在的接口先做最小约定，不新建万能管理器。表现与规则可在同一功能目录内保持清晰边界，不要求 frontend/backend 两个工程。

## 新目录怎样决定归属

“谁负责”填到真实任务和模块说明，文件夹按功能命名，不按成员姓名命名。先看该内容服务谁：玩家专用留在玩家模块，当前地图组装留在地图，确有多个使用者才考虑共享目录。不能靠 `manager/` 或“公共”命名掩盖职责不清。

只做小房间时，不强制建 `ui/`、`shared/`、`addons/`、`network/` 等空目录。初始分工可以让一人负责主场景组装，其余成员在独立子场景中工作；具体模块边界按任务设计决定。

## 迁移前后检查

| 检查对象 | 要留下的证据 |
|---|---|
| 文件与对应 `.uid` | 旧路径→新路径列表、是否有重名、是否保留脚本身份 |
| 资源引用 | 场景/资源中的外部路径、脚本 `load/preload`、主场景与 Autoload 等实际引用已更新 |
| 引擎导入 | 实际引擎版本、导入结果与准确错误；退出码为零也要查看错误日志 |
| 启动与操作 | 主入口和受影响独立场景能否加载；移动/碰撞/交互按任务验证 |
| 多人相关路径 | 只在本次影响 RPC、节点层级或生成入口时补验，不能把单机通过写成联机通过 |
| 外置素材 | 获取版本、共享路径与本机 `res://` 路径一致；不因迁移而把素材强制加入 Git |
| 文档与任务 | 运行说明、文件范围与接口链接仍能定位到新路径 |

移动目录时不靠删除旧目录再从头拼一份来“解决引用”；保留可恢复成果，查看实际差异。没有编辑器可用时可以做范围明确的文件移动与文本修复，但必须准确标注未完成引擎导入/运行检查。

## 交接材料样例

```text
本次模式：实际初始化 / 目录新增 / 资源迁移 / 仅方案。
仓库根：实际路径。
Godot 工程根：实际英文路径；project.godot 位置。
运行：实际版本、主场景、操作和验证命令。
结构：只列已有目录，解释所属模块与必要维护者。
变化：新增路径；或旧路径→新路径。
验证：已通过 / 已失败 / 未执行；对应实际入口和行为。
素材：无外部依赖；或实际素材包版本与获取方式。
下一步：另一个成员应在哪个目录继续，哪些公共文件需协调。
```

上面是模板，不把材料准备说成实际建工程或已迁移资源。
