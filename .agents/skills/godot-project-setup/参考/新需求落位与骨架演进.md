# 新需求落位与骨架演进

按需求归属决定改动，不把示例目录当成强制脚手架。先读取实际项目 AGENTS、共同目标、结构说明、相关接口与任务；不存在这些资料时基于真实代码和用户目标继续，不要求取得作者项目。

## 决定是否新增目录

| 需求性质 | 优先选择 | 需要明确 |
|---|---|---|
| 扩展现有机制或修 Bug | 放回已有功能模块 | 现有入口与验收，不重排目录 |
| 新物品种类、参数或皮肤 | 扩展既有定义/表现资源 | 定义只读、实例状态独立；通常不新建系统 |
| 新的独立玩法职责 | 按需新增 features/<feature>/ | 输入输出、唯一状态写入者、调用方与验证入口 |
| 地图专属摆放与环境 | worlds/<world>/ | 地图只组装，不复制通用玩家/背包实现 |
| 界面与本机反馈 | ui/ 或实际已有所属目录 | 只展示已确认状态、发送意图，不确认共享结果 |
| Steam 等运输适配 | 扩展现有 session/network 位置 | 连接生命周期与身份映射，不另造玩法权威入口 |
| 公共协议/状态归属/依赖方向改变 | 先写最小架构调整 | 旧→新接口、受影响调用方、迁移顺序与回归 |

有实际使用者和独立职责才建目录。文件夹按功能命名，不按成员；一个模块可以由多人分任务维护，不等于一人独占一整个顶层目录。没有职责归属时不要直接丢到 shared、utils、manager 或 Autoload。

## 开发前留下最小落位决定

在任务卡或简短说明中写：需求对应的共同目标；复用/新增模块及原因；负责与不负责；新增/修改路径；状态拥有者与公开接口；受影响调用方；本次公共文件编辑者；验证入口。小任务可用一段话，不强制另外创建设计文档。

局部实现可直接继续；只有确实改变架构时才展开完整设计。用户任务已授权的必要跨文件改动可以完成，不因触及公共文件自动要求再次许可；如存在实际并行写入、未明确的玩法选择或任务范围冲突，先说明最小协调项，继续独立部分。

## 避免入口成为所有业务的容器

main 组合依赖与组织当前流程。新增敌人、救援、撤离机制时优先放到所属模块，由 main 接入。不要因“main 太长”一次性搬走全部原型代码；在真实变更触及其职责时做最小提取，保留接口及可验证基线。规则与表现是职责维度，不要求每模块都建 rules/view/network 三层空目录。

新增文件、目录或接口后同步实际结构说明与任务；改变方向时更新项目共识。迁移既有资源按目录操作参考核对 .uid、res://、场景、Autoload、RPC 路径和全部调用方，不只验证文件是否存在。

## 参考案例：根目录工程与 docs

下面取自一个灰盒工程的职责布局，仅作映射示例；不依赖该工程路径，也不宣称任何读取本技能的项目已经实现这些功能。

```text
project.godot                res:// 从根目录计算
app/main.tscn                主入口
app/main.gd                  编排与模块接线
app/network/session.gd       会话/运输入口
features/player/             玩家主体、移动及专用表现
features/inventory/          背包机制
worlds/prototype_room/       地图与环境
ui/                          显示与意图
tests/                       实际验证入口
docs/design/                 项目共识、结构、模块接口
docs/plans/                  日期化计划
docs/tasks/                  任务范围、主责、状态
docs/verification/           日期化验证证据
```

已有上述布局就沿用，不套成 game/game 或另建第二个工程。已有 game/project.godot 或其他合理布局也不迁移。文档路径从项目入口发现，不硬编码某个日期或中文文件名；以正文维护日期保留长期共识的单一来源。

例如鬼怪追逐落在 features/enemies，地图提供环境，房主确认结果；背包外观改动只动 UI/表现；Steam 接入优先扩现有网络适配。Steam 是否是正式目标、具体人数和版本都从当前项目读取，不由通用技能替项目决定。
