# 团队分工与协作约定

更新：2026-10-18。下表是认领方向，不是已分配给真实成员。成员在任务看板填写主责和备份，同一任务只设一个最终跟进人。

| 方向 | 可独立推进的范围 | 必须先约定的边界 |
|---|---|---|
| 工程与联机 | app/network、隔离联机测试、Steam 技术实验 | RPC、版本、开始/退出；main 修改由集成人协调；至少一位备份掌握 |
| 物品与背包 | features/inventory | 定义与实例 ID、容量接口、唯一归属；不得直接改 HUD/地图 |
| 怪物与救援 | features/enemies、features/rescue；跨模块生命周期改动先协调 match | 房主确认目标/命中；倒地、救起、死亡的状态转换 |
| 地图与视听 | worlds、features/player/actor_view、features/audio | 世界尺度、碰撞、脚点；角色物理/输入调整需与编排方协调 |
| 玩法、界面与验收 | ui、tests、docs；协调撤离与结算 | UI 仅发意图；规则接入 match，main 仅组合；共享修改由集成人执行 |

所有方向共同遵循[项目共识与目标](2026-10-18-项目共识与目标.md)，Steam 跨网络联机是正式目标，不因某个模块仅在局域网通过就标记总体达成。

## 开工与交接

1. 从[任务跟进](../tasks/2026-10-18-任务跟进.md)选一个小交付，写清目标、不做项、主责、备份、依赖和允许改动文件。
2. 每人独立 clone 或 worktree、独立功能分支；不能多人共用同一个目录切分支。
3. 先明确公开接口、输入输出、状态写入者、清理规则与验收步骤，再并行实现。接口有变化先更新设计并通知受影响的队友。
4. 公共 `project.godot`、`app/main.gd`、RPC 契约和同一地图文件，每轮指定一位集成人编辑。其他人提交具体接入需求，不各造一套入口。
5. 交接写实际改动、运行入口、已通过与未执行、依赖版本和下一步；作者自测不写成他人审核。完成条件看实际证据。

## 代码提交与 main

全员可合 main，不要求角色权限校验或强制 PR。仓库建立后采用：功能分支开发 → 明确文件暂存与 commit → fetch 最新 main → rebase origin/main → 处理冲突并复验 → 普通快进合并/推送 main。主线前进后需再次同步验证，不强推 main。仅本地任务不自动变成远端发布。

提交前检查 diff、暂存清单与所有待推送提交。素材、工具设置、缓存、导出物和大文件不进仓库；`.gitignore` 不按大小过滤，也不会移除已跟踪文件。达到 10 MiB 的文件外置，不改用 LFS。保留本地文件并交接外部依赖版本与还原路径。

## 例会与任务更新

每次先看能运行的版本和阻断问题，再确定下一轮一个体验目标与少量任务。会后把日期、决定、责任人、共享文件编辑者和待确认项记入 docs/meetings 下的中文文件。任务状态及时从进行中改为已实现待验证或已验收，不以“代码写完”替代试玩。

给 AI：项目共识与目标 + skill + 当前任务卡 + 相关设计链接 + 文件范围 + 验收。技能可以自动匹配，但显式点名更确定；技能不替代任务上下文和独立工作目录。
