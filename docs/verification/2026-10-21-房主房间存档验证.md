# 房主房间存档验证

日期：2026-10-21；任务 SAVE-011；基线 04d0ead；分支 codex/host-room-saves。当前 AI 统一修改 Main、Session、Steam 身份与 persistence。用户本轮要求实现修复；仅本地提交，不延续此前功能的远程推送授权。

## 原因和行为

旧 Session._on_peer_connected 每次调用 add_player，直接重建默认背包和仓库；离开时 remove_player 没有持久记录。Main 的旧个人档只保存房主本人，客机不能保存，临时 peer ID 也不能识别重进的同一人。

现将房主 Steam 账号作为稳定房间键，成员账号作为档案键，由房主保存。建新大厅仍读取同一房主文件；不同房主使用不同文件，同一成员在各房间的背包、装备、弹匣、状态和仓库互不串档。返回基地出生，保留物品和状态，不恢复旧地图中的位置；该任务不增加世界掉落/战役持久化。离线个人档与房间档分别处理，客机离开房间不会用房主数据覆盖本机离线人物。

运行位置 user://rooms/steam_<房主账号>.json，数据包含 version、owner、profiles；profiles 的键由 SteamService.peer_identity 从已验证大厅成员及 get_steam_id_for_peer_id 获取，绝不接受客机自报档案或昵称充当身份。原有 UI 意图 → Session 验证 → BaseModel 确认继续成立；同一身份同时出现两次拒绝准入，防止两份活跃物品副本。

Profile.capture 深拷贝；valid 先验证完整房间的每份背包/装备/仓库及数值，再 apply，apply 重发当前运行 UID 并映射弹匣。RoomStore.checkpoint 一起收集所有在线成员，保留离线成员；消费、转移、拾取等成功动作立即落盘，射击/持续状态每 5 秒补存，玩家断线、手动保存、正常关房/退出时提交最新状态。服务器全退出后也可恢复原成员。操作失败不生成新档覆盖。

## 文件保护与迁移

首次无房间档时，从原 a1_bunker_profile_v1.json 导入房主本人背包和仓库一次，原文件保留。已有房间档时不再读取旧个人档，避免旧食物补回；旧版本未曾保存的客机历史无法反推，仅从新版首次进入时建立记录。

写入同目录 .tmp、flush/检查错误、保留上一份 .bak，最后 rename 替换正式文件，避免先截断当前档。Windows 连续替换已实际验证。坏 JSON、物品非法、缺 owner 档、owner 不匹配均阻止建房并提示，保持原文件；不自动读取旧备份导致物品回滚。缺主档但已有备份也视为需要人工恢复，不冒充新房间。文件重命名语义参考 [Godot DirAccess](https://docs.godotengine.org/en/4.5/classes/class_diraccess.html)。

存档保存在房主本机；换房主电脑/用户目录时需复制 rooms 目录。首次创建档仍需可写磁盘，保存失败会显示错误。正常物品动作即时落盘；强制结束/断电可能失去最近 5 秒的持续状态或射击进度，不把正常退出保证扩大为电源故障事务保证。
